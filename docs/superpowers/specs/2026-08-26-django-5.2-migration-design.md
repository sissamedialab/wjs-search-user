# wjs-search-user: Django 5.2 Migration — Design

## Context

This is the second of five independent `wjs-*` plugin repos being ported to Django 5.2, following
the core `janeway-5.2` migration (Django 4.2.30 → 5.2.17, Python floor `>=3.9` → verified
`3.10`–`3.13`) on branch `migration/1.8-phase7-pep440-compat-release`, and after `wjs-themes`
(see its own spec, `wjs-themes/docs/superpowers/specs/2026-08-26-django-5.2-migration-design.md`).

`wjs-search-user`'s `setup.cfg` declares no `wjs-*` dependencies, which initially suggested it was
an independent leaf like `wjs-themes`. Investigation for this spec found that's true only at the
packaging level — see "Repo shape" below for the real, undeclared runtime coupling this creates.

**Amendment (at planning time):** the Python floor across all five repos is now confirmed as
**3.11** (not the 3.10 floor assumed above, carried over from the core migration's own verified
range). This repo declared no `python_requires` at all, so this is a new addition — see the
implementation plan's Task 2.

## Goal

Make `wjs.user_search` work correctly under Django 5.2, with no behavioral change, code-verified
now. Full live/functional verification is **deferred** (see Verification) because this app cannot
actually load until two other repos in this same migration effort are also Django-5.2-compatible.

## Repo shape (as found)

- Distributed as a standalone installed Django app (`wjs.user_search`), not a Janeway "plugin"
  under a `plugins/` directory (unlike `wjs_submission`).
- Package name in `setup.cfg` is `wjs.user_search`, version `2.0.4.dev1`. `setup.cfg` declares
  **no `install_requires` at all** — not Django, not `requests` (imported directly in `views.py`),
  not any `wjs-*` package.
- Python surface, 7 non-trivial files (`models.py` and `tests.py` are empty stubs — see below):
  - `wjs/user_search/apps.py` — `AppConfig.ready()` imports `wjs.user_search.urls`
  - `wjs/user_search/urls.py` — builds `urlpatterns` with `django.urls.re_path` (already the
    modern API, not the deprecated `django.conf.urls.url`), then does
    `include_urls.urlpatterns = urlpatterns` — mutates a shared list on Janeway's
    `core.include_urls` module at import time. This is an existing Janeway plugin-registration
    convention, not something this port changes.
  - `wjs/user_search/views.py` — `FormView`/`View`-based views, raw SQL via
    `Account.objects.raw()` / `Collaboration.objects.raw()` against `core_account` and
    `wjs_submission_collaboration`, plus a live HTTP call to the Crossref funders API via
    `requests`. Imports, at module level: `core.models.Account`, `submission.models.ArticleFunding`
    (from Janeway core), **`plugins.wjs_submission.models.Collaboration`** (from
    `wjs-submission-project`), and **`wjs.jcom_profile.models.Correspondence`** (from
    `wjs-profile-project`).
  - `wjs/user_search/forms.py`, `widgets.py` — plain `forms.Form` classes and `Input`-subclass
    widgets with declarative `Media` inner classes (unaffected by Django 5.2).
  - `wjs/user_search/admin.py` — empty, no models registered.
  - `wjs/user_search/models.py` — empty (`# Create your models here.`); `migrations/` contains
    only `__init__.py`.
  - `wjs/user_search/tests.py` — an unused `django.test.TestCase` import, no actual tests.
- **Undeclared runtime coupling**: because `apps.py.ready()` imports `urls.py`, which imports
  `views.py`, this app cannot be loaded by Django's app registry unless both
  `plugins.wjs_submission` (from `wjs-submission-project`) and `wjs.jcom_profile` (from
  `wjs-profile-project`) are already installed and importable — despite neither being declared in
  `setup.cfg`. Per your confirmation, this is expected under Janeway's plugin architecture:
  Janeway injects plugins into the Python path and `INSTALLED_APPS` directly, not via pip
  dependency declarations, so apps routinely cross-import each other's models without a formal
  dependency graph. **This is not being changed as part of this port.**
- No automated tests exist (`tests.py` is a stub) and no `.claude/rules/` directory documents a
  testing convention for this repo (unlike `wjs-themes`).
- CI (`.gitlab-ci.yml`) runs only package build/deploy — no lint stage, no test stage — on the
  `python:3.11` image. Its own comment says: "Not running any tests (at the moment), because they
  require a working installation of Janeway, with this django app installed."

## Approach

Same tool-assisted method as `wjs-themes`: run `django-upgrade --target 5.2` and `ruff` over the 7
non-trivial files to catch mechanical rewrites, then manually review all of them. A first read
found nothing obviously at risk — `urls.py` already uses `re_path` (not the deprecated
`django.conf.urls.url`), and the `Media` inner classes in `widgets.py` are unaffected by 5.2 — so
this is expected to be small, similar in shape to `wjs-themes`.

Considered and rejected:
- **Reorder this repo to after `wjs-submission-project`/`wjs-profile-project`**: would allow
  immediate live verification, but loses the ordering benefit of doing the smaller/simpler repos
  first, and the static-only pass here doesn't block on it — this repo's Python surface is small
  and self-contained enough to review now regardless of whether its runtime imports currently
  resolve.
- **Verify now against the current, not-yet-ported `wjs-submission-project`/`wjs-profile-project`**:
  rejected — a failure to load in that setup could be caused by *their* pre-existing Django 4.2-only
  code, not by anything in this repo, giving a misleading signal. Better to defer to a clean
  all-parties-ported check.
- **Add the undeclared dependencies to `setup.cfg`**: rejected per your direction — this doesn't
  match how Janeway plugins are actually wired (path injection, not pip), so declaring them would
  misrepresent the real installation mechanism without changing it.

## Changes

1. **Python fixes** in the 7 files listed above, as found by `django-upgrade --target 5.2` +
   manual review. Scope is whatever those tools/review turn up.
2. **`setup.cfg`**: no `install_requires` changes (see rejected alternative above). Bump `version`
   from `2.0.4.dev1` to a release version (proposed: `2.1.0`), so `wjs-submission-project`'s
   `wjs-user-search >= 2.0.3` pin remains satisfiable against a known-Django-5.2-compatible
   release once tagged and uploaded.
3. **`.gitlab-ci.yml`**: bump `default.image` from `python:3.11` to `python:3.13`, matching
   `wjs-themes` and the core repo's verified 3.10–3.13 floor.
4. No changes to `wjs-submission-project`, `wjs-profile-project`, or any other repo.

## Verification

**Now (static):**
1. Run `django-upgrade --target 5.2` and `ruff` over the 7 files; apply and review fixes.
2. Manually read all 7 files for anything the tools can't catch.
3. Run whatever lint tooling this repo has configured (to be confirmed at implementation time —
   no `.claude/rules/` exists here to document it, unlike `wjs-themes`).

**Deferred (live/functional) — explicit open item, not performed in this spec's implementation:**
Once `wjs-submission-project` and `wjs-profile-project` are also Django-5.2-compatible, do a
combined live check: install all three (`wjs-themes`, `wjs-search-user`,
`wjs-submission-project`, `wjs-profile-project`) into the `janeway-5.2` checkout, confirm
`wjs.user_search` loads without import errors, and exercise its endpoints (`/user-search/`,
typeahead search, collaboration search, funding search) in a browser against real data. This
combined check is tracked as follow-up work at the end of the whole 5-repo effort, not owned by
this spec's implementation.

## Out of scope

- The deferred live verification itself (tracked above, not performed here).
- Porting `wjs-utils-project`, `wjs-submission-project`, or `wjs-profile-project` — each gets its
  own spec.
- Declaring cross-plugin dependencies in `setup.cfg` (see rejected alternative above).
- Adding an automated test suite to `wjs-search-user`.
- Changing the `include_urls.urlpatterns` mutation pattern in `urls.py` — pre-existing Janeway
  plugin-registration convention, unaffected by Django 5.2.
